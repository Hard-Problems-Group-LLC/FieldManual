# Alembic

## Use When

Use Alembic to manage versioned relational schema changes for applications
that use SQLAlchemy. Do not replace migration history with startup-time schema
mutation or manual edits to production databases.

## Project-Declared Version Policy

Declare an Alembic version compatible with the project's supported SQLAlchemy
major version and Python baseline. Upgrade Alembic with the ORM and database
driver stack, then revalidate migration templates.

## Configuration Baseline

- Keep migration configuration and revision files in version control.
- Maintain one documented source for model metadata used by autogeneration.
- Review autogenerated revisions before merging them.
- Separate schema changes from irreversible data transformations when doing so
  makes deployment and recovery safer.
- Keep database URLs out of tracked configuration and inject them through the
  project's approved runtime configuration.

## Security and Operations

Run migrations with a deliberately scoped database role. Record migration
start, completion, revision, and failure in deployment logs without exposing
credentials.

Do not let multiple application instances race to apply the same migration
unless the deployment design explicitly coordinates that behavior.

## Validation

- Upgrade a fresh database from the base revision to the current head.
- Upgrade a representative existing database through the supported history.
- Check that application models and migration history do not drift.
- Exercise important data transformations with realistic fixtures.
- Verify the deployment process stops safely when a migration fails.

Exact commands and automation are project-owned. FieldManual ships no Alembic
verifier.

## Failure Handling and Rollback

Choose roll-forward or downgrade behavior explicitly for each risky change.
Back up affected data before destructive transformations. Never treat a
hand-edited live schema as a substitute for a reviewed corrective revision.

## Maintenance Risks

- Unreviewed autogenerated operations.
- Multiple migration heads without an intentional merge.
- Irreversible transformations with no recovery plan.
- Schema mutation hidden in application startup.
